## The Problem

The web is asynchronous.  Clicking a button _does something_.
**The amount of _somethings_ keeps increasing, along with their failure states.**
Telling the user that something is _Loading..._ is not enough.
Nor is _Oops, something went wrong_.

> Is it?  Is it _really_ that big of a problem?
> – Everyone

No. You wrap up that asynchronous complexity however you want it:

- Multiple components like `SubmitButton`, `CreateProjectButton`, `DeleteUserButton`, `UploadAvatarButton`, etc.
- Wrap the complexity inside a TanStack `useMutation` or  `useCreateProject()` hook.

There's a point where you need more than communicate _state_: **you need to communicate _progress_**.

## The AJAX Button

It could be validating & submitting a form, fetching some data, or mutatating some state.
We realized we didn't just _submit_ the form, but needed to see if it _worked_:

<Example code={AJAXButtonDemoSource} lang="tsx">
  <AJAXButtonDemo client:visible />
</Example>

1. Click Subscribe
2. ❌ Error
3. Change email to `new@example.com` and click Subscribe, again
4. ✅ Success (but also ❌ Error!?)

This meant tracking state in the DOM or in the parent component with (many) `useState`.
And, in this case, I (intentionally because it's common) forgot to reset the state between attempts 😣.

Yes, this can be improved with `useReducer`, `useMutation`, or even [state machines](https://github.com/statelyai/xstate).
But this is actually **almost exactly how ~humans~ [agents write code](https://chatgpt.com/share/6a0a8e27-90e0-8332-b5d4-7ed43a16fff4)**.

Now we're up to 4 states: <code>IDLE</code>, <code>PENDING</code>, <code>SUCCESS</code>, and <code>ERROR</code>.

## Reducing Conditional Complexity with PromiseButton

With fewer `useState` calls, the next source of complexity is conditional rendering (or _ternary soup_ 🍲).
We could replace this button with a specialized `SpamSubscribeButton` component, but then we'd do that _everywhere_.

**What if we could have a generic `PromiseButton` that had handled each state explicitly**?

### Insipiration

Let's look at [Sonner](https://sonner.emilkowal.ski/)'s `toast.promise` API:

```tsx
toast.promise(promise, {
  loading: 'Loading...',
  success: (data) => {
    return `${data.name} toast has been added`;
  },
  error: (error) => error.message,
});
```

See for yourself, this neatly captures the `LOADING`, `SUCCESS`, and `ERROR` states:

## Cancellation

When making a `fetch` request, we can now [`abort()`](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal#examples)
it, adding a _5th_ state to our button: `CANCELLED`.

Luckily, TanStack Query supports `signal` for [cancelling queries](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation).
When a component unmounts, it's automatically cancelled.
In this case, I'll _manually_ cancel the query when the button is clicked again:

Instead, I can accomplish this by passing in a `signal` to the `onClick` handler _and_

## Inject Another Solution

Let's go back to the [Sonner](https://sonner.emilkowal.ski/)'s `toast.promise` API,
but also combine it with the inferred `Button` behavior.

**What if the behavior could update the UI without creating a new component every time?**

We can do this by injected a 2nd argument `setProps` into the `onClick` handler:


```tsx
<BetterButton onClick={async (event, setProps) => {
  setProps({ children: "Loading...", disabled: true });
  await wait(1000);
  if (Math.random() > 0.5) {
    setProps({ children: "Error! 💥" });
  } else {
    setProps({ children: "Success! 🎉" });
  }
}}>Click me</BetterButton>
```
